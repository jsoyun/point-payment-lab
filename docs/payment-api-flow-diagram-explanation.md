# 결제 API 흐름 다이어그램 해설

## 문서 목적

이 문서는 diagrams.net의 `결제프로젝트`에 작성한 일곱 개 페이지를 글로
설명한다. 그림의 도형을 단순히 나열하기보다 요청이 어떤 순서로 이동하고,
어느 지점에서 문제가 발생하며, 각 개선이 어떤 방어선을 추가했는지를
중심으로 정리했다. 따라서 다이어그램과 함께 포트폴리오에 사용하거나,
그림 없이 현재 결제 개선 과정을 복습할 때 사용할 수 있다.

- [결제프로젝트 diagrams.net](https://app.diagrams.net/#G15VCYdDP6PvsHo-a5TCzJpYTm5Hfbrb9A)
- 1~3차 개선은 실제 코드 구현과 검증을 완료했다.
- `07-4차 Redis 분산락 API 흐름`은 앞으로 구현할 목표 설계이며 현재 동작하는 코드가 아니다.

## 01. Legacy 문제 발생 흐름

Legacy 결제 흐름의 가장 큰 특징은 내부 결제가 성공할 수 있는지 확정하기
전에 외부 바우처 발행 API를 호출한다는 점이다. 사용자가 결제를 요청하면
쇼핑몰 서버는 지갑과 상품, 포인트 잔액을 조회한 후 외부 발행사에 쿠폰
발행을 요청한다. 외부 발행사는 이 요청을 받으면 `provider_voucher`에 발행
결과를 저장하고 바우처 번호와 PIN을 반환한다. 그다음에야 쇼핑몰 서버가
포인트 lot 사용 처리, 출처별 잔액 차감, 전체 잔액 차감, 원장 기록과 구매
내역 저장을 하나의 내부 트랜잭션으로 실행한다.

이 순서에서는 동일한 `orderId`를 가진 두 요청이 거의 동시에 도착했을 때
두 요청 모두 외부 발행 단계까지 통과할 수 있다. 아직 쇼핑몰에서 해당
주문을 누가 처리 중인지 선점한 기록이 없고, 외부 발행사에도 동일 주문을
한 번만 발행하도록 보장하는 장치가 없기 때문이다. 결과적으로 쿠폰 두
장이 먼저 발행된 뒤 두 내부 트랜잭션이 같은 포인트 데이터와 같은 주문
번호를 동시에 변경하려고 경쟁한다.

실제 재현에서는 한 트랜잭션이 `point_source_balance`의 잠금을 가진 채
`voucher_purchase.order_id`의 unique 인덱스를 기다렸고, 다른 트랜잭션은
반대 순서로 잠금을 기다렸다. MySQL은 이 순환 대기를 Deadlock으로 판단해
한 트랜잭션을 rollback했다. 따라서 사용자에게는 한 요청이 HTTP 201로
성공하고 다른 요청이 HTTP 500으로 실패했지만, 외부 발행 요청은 이미 두
번 실행된 상태였다. 실패한 요청의 쿠폰은 별도의 cancel API로 보상
취소되어 외부 DB에는 `ISSUED` 한 건과 `CANCELED` 한 건이 남았다.

잔액 부족 요청에서도 같은 구조적 문제가 나타난다. 포인트로 살 수 없는
상품인데도 외부 쿠폰을 먼저 발행하고, 내부 트랜잭션에서 포인트 부족을
발견한 뒤 rollback과 보상 취소를 수행한다. 즉, 애초에 외부로 보내지 않아도
될 요청이 외부 시스템의 발행과 취소를 모두 발생시킨다. 더 심각하게는
내부 DB rollback이 외부 시스템의 상태를 되돌릴 수 없기 때문에 cancel
호출까지 네트워크 오류로 실패하면 외부에는 사용 가능한 쿠폰이 남고
쇼핑몰에는 구매 기록이 없는 불일치 상태가 생길 수 있다.

이 페이지가 보여주는 핵심은 Deadlock 하나만의 문제가 아니다. 중복 요청
식별 부재, 너무 이른 외부 호출, 그리고 로컬 DB 트랜잭션과 외부 API 사이의
경계가 결합되어 불필요한 발행·취소와 데이터 불일치를 만들 수 있다는 것이
Legacy 흐름의 본질적인 한계다.

## 02. 단계별 개선과 검증 결과

두 번째 페이지는 앞에서 발견한 문제를 한꺼번에 수정하지 않고 방어선을
단계적으로 추가한 과정을 요약한다. 1차 개선은 쇼핑몰 입구에서 동일 주문의
중복 실행을 막고, 2차 개선은 쇼핑몰 방어를 우회해 외부 Mock API를 직접
호출하더라도 쿠폰이 중복 생성되지 않게 한다. 3차 개선은 결제 가능성을
먼저 확인해 실패가 확실한 요청이 외부 시스템에 도달하지 않게 한다.

이 개선을 같은 동시 요청 실험으로 비교했을 때 Legacy에서는 외부 발행이
두 번 실행되고 Deadlock과 보상 취소가 각각 한 번 발생했다. 1차 개선 후에는
외부 발행과 내부 구매가 각각 한 건만 생성되었고 Deadlock과 보상 취소는
발생하지 않았다. 외부 발행 API 자체도 같은 주문으로 동시에 두 번 호출해
검증했으며, 최초 응답과 재요청 응답에 포함된 바우처 번호와 PIN이 같고
`provider_voucher`도 한 행만 저장되는 것을 확인했다. 잔액 부족 실험은
Legacy의 HTTP 500과 발행 후 취소에서 HTTP 422와 외부 호출 0회로 바뀌었다.

다만 이 결과가 모든 동시성 문제를 해결했다는 뜻은 아니다. 현재의
`orderId` 방어는 같은 주문의 재실행을 막지만, 서로 다른 주문 두 개가 같은
지갑 잔액을 동시에 사용하는 상황은 별개의 문제다. 또한 단일 DB 중심의
멱등 처리를 여러 API 서버 환경에서 더 빠르게 조정하고 동일 응답을 재사용하는
Redis 실습도 아직 남아 있다.

## 03. 개선 전 Legacy API 요청·응답 흐름

세 번째 페이지는 첫 번째 페이지의 문제 중 따닥 결제를 시간순 API
시퀀스로 확대한다. 사용자가 같은 `orderId`로 결제 요청 A와 B를 거의 동시에
전송하면 두 요청 모두 Legacy 결제 API에 진입한다. 서버는 각각 지갑, 상품,
잔액을 조회하지만 이 조회 결과만으로는 다른 요청이 같은 주문을 처리 중인지
알 수 없다.

두 요청은 차례로 외부 `issue` API를 호출하고 외부 발행사는 서로 다른
바우처 번호와 PIN을 생성한다. 이 시점에 이미 외부 호출 횟수는 두 번이며
`provider_voucher`에도 동일 주문의 두 발행 결과가 만들어진다. 이후 요청
A와 B가 내부 결제 트랜잭션을 동시에 실행하면서 같은 포인트 행과 주문
unique key를 잠그려고 한다. 한 트랜잭션만 commit되고 다른 트랜잭션은
Deadlock victim이 되어 rollback된다.

사용자는 같은 결제 행위에 대해 HTTP 201과 HTTP 500이라는 서로 다른 응답을
받는다. 실패 요청을 받은 서버는 이미 발행된 두 번째 바우처를 정리하기 위해
외부 cancel API를 호출하고, 해당 외부 바우처는 `CANCELED`가 된다. 내부
구매가 한 건만 남았다는 최종 결과만 보면 중복 결제가 방지된 것처럼 보일
수 있지만, 실제로는 외부 발행 두 번, 불필요한 취소 한 번, Deadlock 한 번이
발생했다. 따라서 DB의 최종 행 개수만이 아니라 외부 API 호출 횟수와 중간
상태까지 함께 관찰해야 이 문제를 정확히 발견할 수 있다.

## 04. 1차 개선: PaymentAttempt 기반 API 흐름

1차 개선에서는 외부 바우처를 발행하기 전에 `payment_attempt`에 주문 처리
상태를 기록한다. 같은 `orderId`의 두 요청이 동시에 들어오더라도
`payment_attempt.order_id`의 unique 제약 때문에 단 하나의 요청만
`PROCESSING` 상태를 선점할 수 있다. 선점 트랜잭션은 외부 API 호출과 분리된
짧은 트랜잭션으로 처리하여, 누가 해당 주문을 실행할지를 먼저 확정한다.

선점에 성공한 최초 요청은 기존 결제 흐름으로 이동한다. 외부 발행사에
`issue`를 한 번 호출하고, 반환된 바우처 번호와 PIN으로 포인트 차감과
`voucher_purchase` 저장을 완료한다. 결제가 성공하면 `payment_attempt`를
`SUCCEEDED`로 변경하고 재사용할 결과를 저장한 뒤 사용자에게 HTTP 201을
반환한다.

동시에 들어온 두 번째 요청은 같은 `orderId`를 INSERT할 수 없으므로 기존
시도 상태를 조회한다. 아직 최초 요청이 처리 중이라면 외부 발행사까지
진입하지 않고 HTTP 409 `PAYMENT_PROCESSING`을 반환한다. 최초 결제가 완료된
뒤 같은 요청을 다시 보내면 새 쿠폰을 발행하지 않고 `SUCCEEDED`에 저장된
바우처 결과를 HTTP 200과 `Idempotency-Replayed: true`로 반환한다. 같은
`orderId`를 사용하면서 상품이나 결제 내용이 다르면 동일 요청의 재시도가
아니므로 HTTP 409 `IDEMPOTENCY_KEY_REUSED`로 거절한다.

실제 동시 HTTP 검증 결과는 한 요청이 HTTP 201, 다른 요청이 HTTP 409였고,
`payment_attempt`, `provider_voucher`, `voucher_purchase`가 각각 한 건만
생성되었다. 포인트도 한 번만 차감되었으며 Legacy에서 발생했던 Deadlock과
보상 취소는 사라졌다.

그러나 이 방어는 쇼핑몰의 멱등 결제 API를 통해 들어오는 요청에 적용된다.
외부 발행 Mock API를 누군가 직접 같은 `orderId`로 두 번 호출하면
`payment_attempt`을 거치지 않기 때문에 외부 시스템에서 쿠폰 두 장이 생길
가능성은 여전히 남아 있었다. 이 한계를 해결한 것이 2차 개선이다.

## 05. 2차 개선: 외부 발행사 멱등 API 흐름

2차 개선은 쇼핑몰뿐 아니라 외부 발행사도 자신의 API 멱등성을 스스로
보장하도록 만든다. 외부 `issue` 요청이 들어오면 발행 서비스는
`provider_voucher.order_id`의 unique 제약을 기준으로 최초 요청인지 확인한다.
최초 요청이면 새 바우처 번호와 PIN을 생성해 한 행을 저장하고 HTTP 201로
응답한다.

같은 `orderId`와 같은 상품 코드가 다시 들어오면 새로운 번호를 생성하지
않는다. 이미 저장된 `provider_voucher`에서 기존 바우처 번호와 PIN을 조회해
HTTP 200과 `Idempotency-Replayed: true`로 그대로 반환한다. 따라서 네트워크
재시도나 동시 호출로 API 요청 자체는 여러 번 도착하더라도 논리적인 발행
결과는 한 장으로 유지된다. 실제 병렬 호출에서도 응답 A와 B의
`voucherNumber`, `pinNumber`가 같았고 DB 행은 한 건이었다.

반면 같은 `orderId`에 다른 상품 코드를 넣은 요청은 단순 재시도로 볼 수
없다. 이 요청까지 기존 결과로 처리하면 클라이언트가 의도한 상품과 실제
발행 상품이 달라질 수 있으므로 HTTP 409 `IDEMPOTENCY_KEY_REUSED`로 거절한다.
즉, 멱등성은 키가 같다는 사실만 보는 것이 아니라 그 키에 연결된 요청
내용도 같은지 확인해야 한다.

1차와 2차는 중복 방어의 위치가 다르다. 1차는 쇼핑몰 결제 전체가 두 번
실행되지 않게 보호하고, 2차는 외부 발행 API에 직접 중복 요청이 도착해도
쿠폰을 한 장만 발행하게 보호한다. 두 계층의 unique 제약을 함께 두어 한쪽
방어를 우회하거나 애플리케이션 장애가 발생했을 때도 최종 데이터의 중복을
제한한다.

## 06. 3차 개선: 외부 호출 전 검증 API 흐름

3차 개선의 목적은 실패가 확실한 결제 때문에 외부 쿠폰을 발행하지 않는
것이다. 사용자가 바우처 구매를 요청하면 서버는 먼저 상품의 판매 가격을
조회하고 요청한 포인트 금액과 일치하는지 확인한다. 이어서 지갑의
`point_balance`가 충분한지 확인하고, 실제 차감에 사용할 수 있는 미만료
`point_lot`의 합계도 결제 금액 이상인지 검증한다.

가격이 다르거나 전체 잔액 또는 사용 가능한 lot이 부족하면 요청은 이
단계에서 HTTP 422로 종료된다. 외부 `issue` API는 호출되지 않으므로
`provider_voucher`와 `voucher_purchase`가 생성되지 않고 포인트 잔액도
변하지 않는다. Legacy에서 10,000포인트 상품을 5,000포인트 잔액으로 구매한
실험은 외부 발행과 취소 후 HTTP 500이었지만, 개선 API에서는 외부 호출
0회와 HTTP 422로 바뀌었다. 사용자는 원인을 설명하는 4xx 응답을 받고,
시스템은 불필요한 외부 비용과 보상 작업을 피한다.

모든 사전 검증을 통과한 요청만 외부 발행사에 전달된다. 서버는 발행 결과를
받은 뒤 내부 포인트 차감과 구매 저장을 commit하고 HTTP 201을 반환한다.
이 순서는 외부 호출의 대상을 줄이는 데 효과적이지만, 사전 조회 자체가
최종 잔액 차감의 동시성 안전성을 보장하지는 않는다. 잔액을 확인한 직후
다른 주문이 먼저 같은 잔액을 사용할 수 있기 때문이다. 이를
check-then-act 경쟁 조건이라고 하며, 실제 차감 시점에는
`WHERE balance >= amount` 조건부 UPDATE나 row lock 같은 DB 차원의 보호가
추가로 필요하다.

## 07. 4차 개선 설계안: Redis 분산락 API 흐름

이 페이지는 구현 결과가 아니라 앞으로 실습할 목표 구조다. 여러 API 서버
인스턴스 A와 B가 실행되는 환경에서 클라이언트가 동일한
`Idempotency-Key`로 요청을 재전송했다고 가정한다. 두 서버의 Java 메모리는
서로 공유되지 않기 때문에 `synchronized`나 `ReentrantLock`만으로는 다른
서버에서 처리되는 두 요청을 조정할 수 없다. 두 서버가 공통으로 접근하는
Redis의 lock을 사용하는 이유가 여기에 있다.

각 서버는 먼저 Redis에서 해당 멱등키의 완료 응답 캐시를 조회한다. 이미
결제가 끝난 요청이면 외부 API나 MySQL에 다시 접근하지 않고 저장된 HTTP
status와 response body를 반환한다. 캐시가 없다면 같은 키에 대한 Redisson
분산락 획득을 시도한다. 서버 A가 lock을 획득하면 서버 B는 같은 lock이
해제될 때까지 기다리거나 정책에 따라 처리 중 응답을 반환한다.

서버 A는 lock을 획득한 뒤 곧바로 결제를 실행하지 않고 Redis와 MySQL을
다시 조회한다. lock을 기다리는 사이 다른 요청이 결제를 완료했을 수 있기
때문에 필요한 double check다. DB에도 결과가 없다면 `payment_attempt`을
선점하고 상품과 포인트를 검증한 뒤 외부 발행 API를 호출한다. 이후 잔액은
`UPDATE point_balance SET balance = balance - :amount WHERE id = :id AND
balance >= :amount` 같은 조건부 UPDATE로 차감한다. 변경된 행이 한 건이면
차감 성공이고 0건이면 다른 주문이 잔액을 먼저 사용했거나 잔액이 부족한
것이므로 결제를 중단한다.

구매 저장과 DB commit이 완료되면 원본 HTTP status와 response body를 DB에
보관하고 Redis에도 TTL이 있는 완료 응답 캐시를 저장한다. 그다음 분산락을
해제하고 최초 요청에 HTTP 201을 반환한다. 대기하던 서버 B는 lock 해제 후
캐시를 다시 확인해 동일한 status와 body를 반환한다. 이 설계가 목표로 하는
멱등성은 단순히 중복 결제가 생기지 않는 것을 넘어, 같은 요청을 여러 번
보내도 클라이언트가 동일한 결과를 받도록 하는 것이다.

Redis와 DB는 서로 대체 관계가 아니다. Redis lock은 여러 서버의 동시 실행을
빠르게 조정하고 결과 캐시는 반복 조회와 응답 시간을 줄인다. 하지만 lock
TTL 만료, Redis 재시작, 네트워크 장애나 캐시 eviction이 발생할 수 있으므로
`payment_attempt`과 unique 제약은 최종 진실이자 fallback으로 남아야 한다.
또한 Redis lock은 같은 멱등키의 중복 실행을 제어하지만, 서로 다른 주문이
같은 지갑을 동시에 사용하는 문제는 해결하지 않는다. 그 문제는 조건부
UPDATE나 DB row lock이 담당한다.

## 전체 개선 흐름 정리

이 프로젝트의 개선은 하나의 기술로 모든 문제를 해결하는 방식이 아니다.
쇼핑몰의 `payment_attempt`은 결제 요청 전체의 중복 실행을 막고, 외부
발행사의 unique 제약은 쿠폰 발행 자체의 중복을 막는다. 사전 검증은 실패가
확실한 요청을 외부로 보내지 않으며, 향후 조건부 UPDATE는 실제 잔액 차감
시점의 경쟁을 제어한다. Redis와 Redisson은 여러 서버가 같은 멱등 요청을
처리할 때의 조정과 응답 재사용을 담당하고, DB 기록은 장애 상황에서도
복구할 수 있는 최종 근거로 유지한다.

따라서 포트폴리오에서는 “Redis를 도입해 중복 결제를 해결했다”라고 한 문장으로
설명하기보다, 문제의 종류에 따라 서로 다른 방어선을 배치했다는 점을
강조하는 것이 적절하다. 현재까지 실제 구현·검증한 범위는 1차
`PaymentAttempt`, 2차 외부 발행 멱등성, 3차 외부 호출 전 검증이며, 4차
Redis 분산락·결과 캐시와 조건부 잔액 차감은 다음 구현 및 검증 대상이다.
