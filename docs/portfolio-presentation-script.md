# Point Payment Lab 포트폴리오 발표 대본

이 문서는 `output/pdf/point-payment-lab-portfolio.pdf`의 현재 15페이지 구성에
맞춘 발표 대본이다. 각 페이지는 `핵심 메시지 → 발표 대본 → 전환 문장 → 예상
질문` 순서로 설명한다.

## 1페이지. 표지

### 핵심 메시지

Legacy 결제 문제를 직접 재현하고 요청 순서를 단계적으로 바꾼 백엔드 개선 프로젝트다.

### 발표 대본

“Point Payment Lab은 쇼핑몰 포인트로 외부 쿠폰을 구매하는 결제 흐름을 Spring
Boot와 MySQL로 재현한 프로젝트입니다. 단순 기능 구현이 아니라 동일 주문의 동시
요청, 외부 쿠폰 중복 발행, Deadlock, 잔액 경쟁을 실제로 발생시킨 뒤 요청·응답과
DB 상태가 왜 달라졌는지 증명하는 데 초점을 맞췄습니다.

개선은 payment_attempt, 외부 발행사 orderId 방어, 외부 호출 전 검증, Redis
분산락과 결과 cache, MySQL 조건부 UPDATE 순서로 진행했습니다.”

### 전환 문장

“먼저 흐름도에 등장하는 시스템들이 각각 무엇을 의미하는지 설명하겠습니다.”

## 2페이지. 프로젝트 목적과 시스템 역할

### 핵심 메시지

각 시스템이 담당하는 경계와 책임을 먼저 이해해야 개선 흐름을 읽을 수 있다.

### 발표 대본

“Client는 웹 UI, curl, 테스트 스크립트처럼 요청을 보내는 호출자입니다. Shopping
API는 Spring Boot Controller 영역으로 HTTP 입력과 출력을 담당합니다. Application은
Service 영역으로 결제 순서를 결정합니다. Shopping API와 Application은 별도 서버가
아니라 같은 Spring Boot 애플리케이션 안의 서로 다른 계층입니다.

MySQL은 포인트 잔액, 원장, 구매 기록과 최초 결제 응답을 영구 보존합니다. 외부
쿠폰 발행사는 실제 외부 업체를 프로젝트 내부의 Provider Mock API로 재현했습니다.
같은 프로젝트에서 실행되지만 쇼핑몰 DB 트랜잭션 밖의 외부 시스템으로 취급합니다.”

### 예상 질문

**왜 외부 발행사를 Mock으로 만들었나요?**
실제 업체 없이도 HTTP 성공 후 내부 DB 실패, 중복 호출, 보상 취소처럼 시스템
경계에서 생기는 문제를 반복해서 검증하기 위해서다.

## 3페이지. 기술 스택과 단계별 구현

### 핵심 메시지

사용 기술을 나열하지 않고 각 기술이 해결한 경쟁 조건과 시스템 경계를 연결한다.

### 발표 대본

“백엔드는 Java 17, Spring Boot, Spring Data JPA와 TransactionTemplate로
구현했습니다. MySQL 8과 Flyway로 잔액·원장·구매·결제 시도 스키마를 관리했고,
Docker Compose로 MySQL과 Redis를 구성했습니다.

1차에서는 payment_attempt unique와 saveAndFlush, 2차에서는 외부 발행사
orderId unique, 3차에서는 balance와 lot 사전 검증을 구현했습니다. 4차에서는
Redisson RLock과 Redis 결과 cache, MySQL 최초 응답 저장을 결합했습니다. 5차에서는
조건부 UPDATE로 서로 다른 주문의 잔액 경쟁을 막았습니다.

Redis를 사용한 이유는 여러 Spring Boot 인스턴스가 Java 메모리를 공유할 수 없기
때문입니다. Redis 분산락으로 같은 요청의 동시 실행을 하나로 줄이고, 완료 결과를
cache해 DB 중복 저장 시도와 조회를 줄였습니다. 다만 Redis 장애에도 안전해야 하므로
최초 응답은 MySQL에 영구 보존했습니다.”

### 전환 문장

“이제 개선 전 Legacy API의 요청 순서부터 보겠습니다.”

## 4페이지. Legacy 외부 HTTP와 MySQL 트랜잭션 불일치

### 핵심 메시지

외부 쿠폰 발행이 내부 포인트 차감보다 먼저 실행된다.

### 발표 대본

“Legacy API는 지갑과 상품, 잔액을 조회한 뒤 외부 발행사에 쿠폰을 먼저 요청합니다.
쿠폰 번호와 PIN을 받은 다음 쇼핑몰 MySQL에서 lot, 원장, 잔액과 구매 기록을
변경합니다.

문제는 내부 결제 트랜잭션이 rollback되더라도 외부 발행사에서 이미 발급한 쿠폰은
자동 취소되지 않는다는 점입니다. 쇼핑몰 MySQL 트랜잭션과 외부 HTTP 호출은 하나의
ACID 트랜잭션이 아니므로, 실패하면 별도의 쿠폰 취소 API를 호출해야 합니다.”

### 예상 질문

**왜 DB rollback으로 외부 쿠폰도 취소할 수 없나요?**
rollback은 쇼핑몰 MySQL 트랜잭션 안의 변경만 되돌린다. 외부 시스템에서 이미
완료한 HTTP 요청은 별도의 보상 요청 없이는 되돌릴 수 없다.

## 5페이지. 동일 orderId 동시 요청의 쿠폰 중복 발행과 Deadlock

### 핵심 메시지

쇼핑몰 구매 1건만 보면 외부에서 쿠폰이 2장 발급된 사실을 놓칠 수 있다.

### 발표 대본

“같은 orderId로 두 요청을 동시에 보냈습니다. 두 요청 모두 외부 쿠폰 발행까지
통과해 서로 다른 쿠폰 두 장이 만들어졌습니다. 내부 트랜잭션에서는 lock 순서가
엇갈려 한 요청은 HTTP 500 Deadlock, 다른 요청은 HTTP 201을 받았습니다.

최종적으로 쇼핑몰 구매는 1건이지만 외부에는 ISSUED 1건과 보상 취소된 CANCELED
1건이 남았습니다. 따라서 성공 기준을 최종 구매 행 수뿐 아니라 외부 부작용까지
확장해야 한다고 판단했습니다.”

### 전환 문장

“첫 번째 개선은 외부 쿠폰을 호출하기 전에 한 요청만 주문 처리권을 얻도록 하는 것입니다.”

## 6페이지. payment_attempt unique와 saveAndFlush 실행권 선점

### 핵심 메시지

같은 orderId를 payment_attempt에 먼저 저장한 요청만 실제 결제를 실행한다.

### 발표 대본

“요청을 받으면 외부 쿠폰을 발행하기 전에 payment_attempt에 PROCESSING 상태를
먼저 저장합니다. orderId에는 unique 제약이 있어 먼저 저장한 요청은 처리권을
선점하고, 다른 요청은 중복 저장 충돌로 HTTP 409에서 멈춥니다.

구현에서는 `saveAndFlush`를 사용했습니다. JPA의 `save`는 엔티티를 영속성
컨텍스트에 등록하지만 INSERT SQL 실행이 트랜잭션 종료 시점까지 늦어질 수 있습니다.
반면 `saveAndFlush`는 INSERT SQL을 즉시 MySQL로 보내므로, 외부 쿠폰 발행 전에
orderId 선점 성공 또는 unique 제약 충돌을 확인할 수 있습니다.

정확히 말하면 `saveAndFlush` 자체가 선점을 제공하는 것은 아닙니다. 선점은
`payment_attempt.orderId`의 unique 제약을 이용해 한 요청만 INSERT에 성공하게
만드는 설계입니다. `saveAndFlush`는 그 INSERT와 충돌 확인 시점을 외부 API
호출보다 앞으로 당기는 역할을 합니다.

여기서 flush는 commit이 아닙니다. flush는 SQL을 DB에 전달해 제약조건을 확인하는
시점을 앞당기는 동작이고, commit은 트랜잭션 변경을 최종 확정합니다. flush 이후에도
트랜잭션이 rollback되면 해당 INSERT는 되돌아갑니다.

선점에 성공한 요청만 외부 쿠폰을 발행하고 내부 결제를 수행합니다. 결과적으로
외부 발행은 2건에서 1건, Deadlock과 보상 취소는 각각 1건에서 0건으로 줄었습니다.”

### 흐름도 설명 순서

1. 같은 orderId의 요청 A와 B가 동시에 들어온다.
2. 두 요청이 payment_attempt의 PROCESSING 저장을 시도한다.
3. `saveAndFlush`가 INSERT를 즉시 실행한다.
4. 한 요청은 orderId 선점에 성공하고 다른 요청은 중복 저장 충돌을 확인한다.
5. 선점한 요청만 외부 쿠폰 발행으로 진행한다.
6. 두 번째 요청은 HTTP 409 PROCESSING으로 종료된다.

### 예상 질문

**flush와 commit의 차이는 무엇인가요?**
flush는 영속성 컨텍스트의 변경을 SQL로 DB에 전달하지만 트랜잭션을 확정하지 않는다.
commit은 flush를 포함해 트랜잭션을 최종 확정한다. 따라서 flush 후에도 rollback할
수 있다.

**왜 save만 사용하지 않았나요?**
INSERT와 unique 충돌 확인이 늦어지면 코드가 외부 쿠폰 발행 단계까지 진행할 수
있다. 외부 호출 전에 선점 결과를 확정적으로 확인하기 위해 saveAndFlush를 사용했다.

**saveAndFlush가 lock이나 선점을 제공하나요?**
아니다. 실제로 한 요청만 성공하게 만드는 것은 MySQL의 orderId unique 제약이다.
saveAndFlush는 INSERT를 즉시 실행하여 어느 요청이 저장에 성공했고 어느 요청이
중복 충돌했는지 외부 호출 전에 확인하도록 돕는다.

**unique 제약을 선점한다고 말해도 되나요?**
정확히는 unique 자체를 선점하는 것이 아니다. orderId를 먼저 저장해 주문 처리권을
선점하고, unique 제약이 한 요청만 저장에 성공하도록 보장한다.

### 전환 문장

“하지만 쇼핑몰을 거치지 않고 외부 발행사 API를 직접 호출하면 별도의 방어가 필요합니다.”

## 7페이지. provider_voucher orderId unique 외부 발행 멱등성

### 핵심 메시지

외부 발행사도 자신의 DB 경계에서 같은 orderId의 쿠폰을 한 장만 저장한다.

### 발표 대본

“provider_voucher의 orderId를 중복 저장할 수 없게 했습니다. 같은 주문과 같은
상품의 재요청에는 새 쿠폰을 만들지 않고 최초 쿠폰 번호와 PIN을 반환합니다. 같은
orderId로 다른 상품을 요청하면 동일 요청이 아니므로 HTTP 409로 거절합니다.

이로써 쇼핑몰 payment_attempt를 우회해 외부 발행사 API를 직접 호출해도 쿠폰은
한 장만 만들어집니다.”

## 8페이지. point_balance·point_lot 외부 호출 전 검증

### 핵심 메시지

쇼핑몰이 미리 알 수 있는 실패는 외부 쿠폰을 발행하기 전에 차단한다.

### 발표 대본

“기존에는 잔액이 없어도 쿠폰부터 발급한 뒤 내부 결제 실패와 보상 취소가
발생했습니다. 이를 상품 판매가, point_balance, 만료되지 않은 미사용 point_lot
합계를 외부 호출 전에 검증하도록 바꿨습니다.

잔액 부족은 HTTP 422로 종료되고 외부 발행·취소 호출과 내부 데이터 변경은 모두
0건이 됐습니다. 다만 사전 조회만으로 동시 잔액 경쟁까지 해결할 수는 없습니다.”

## 9페이지. Redisson RLock·Redis cache·MySQL 최초 응답 저장

### 핵심 메시지

Redis는 두 서버의 동시 실행을 조율하고 MySQL은 최초 결과를 영구 보존한다.

### 발표 대본

“8080과 8081 두 인스턴스는 Java 메모리를 공유하지 않습니다. 그래서 같은
Idempotency-Key를 기준으로 Redisson 분산락을 획득하고, lock 안에서 Redis cache와
payment_attempt를 다시 확인합니다.

승자만 결제를 실행하고 최초 HTTP 상태와 본문을 MySQL과 Redis에 저장합니다. 두
서버에 동시에 요청해도 외부 쿠폰과 구매는 각 1건이며 두 응답은 같은 HTTP 201과
본문을 반환했습니다.”

## 10페이지. Redis cache miss·TTL 만료·장애 시 MySQL 복구

### 핵심 메시지

Redis가 없어도 MySQL의 최초 응답으로 실제 결제를 재실행하지 않는다.

### 발표 대본

“Redis cache가 있으면 완료 결과를 바로 반환합니다. cache가 만료되면
payment_attempt에서 최초 HTTP 상태와 본문을 읽어 Redis cache를 재생성합니다.
Redis 자체가 중단되면 MySQL 결과를 직접 반환합니다.

따라서 Redis는 성능과 동시 실행 조율을 담당하지만 결제 결과의 최종 근거는
MySQL입니다. 같은 멱등키에 다른 요청 본문을 보내면 HTTP 422로 거절합니다.”

## 11페이지. MySQL 조건부 UPDATE 잔액 경쟁 방어

### 핵심 메시지

서로 다른 주문의 잔액 경쟁은 Redis 멱등락이 아니라 MySQL 자원 변경으로 막는다.

### 발표 대본

“서로 다른 orderId와 멱등키는 서로 다른 Redis lock을 사용합니다. 두 요청이 모두
차감 전 잔액 5,000을 읽을 수 있으므로 `balance >= amount` 조건의 단일 UPDATE로
잔액 확인과 차감을 한 SQL에서 실행했습니다.

변경 행이 1건인 요청만 계속 진행하고 0건인 요청은 HTTP 409로 종료합니다. MySQL이
행을 잠근 뒤 최신 잔액으로 WHERE 조건을 다시 평가하기 때문에 중복 차감을 막습니다.”

## 12페이지. 개선 전후 HTTP·외부 호출·중단 위치 비교

### 핵심 메시지

상태 코드가 달라진 이유는 요청이 실패를 발견하는 위치가 앞당겨졌기 때문이다.

### 발표 대본

“동일 주문 경쟁은 외부 호출 전 HTTP 409로, 잔액 부족은 HTTP 422로 종료됩니다.
완료 요청은 최초 HTTP 201을 그대로 반환합니다. 서로 다른 주문의 잔액 경쟁은 한
요청만 HTTP 201이고 다른 요청은 HTTP 409입니다.

다만 서로 다른 주문은 외부 쿠폰 발행 후 잔액 경쟁에서 실패할 수 있으므로 CANCELED
기록이 남습니다. 외부 발행 전 포인트 예약은 후속 과제입니다.”

## 13페이지. Redis lock·DB unique·조건부 UPDATE 역할 분리

### 핵심 메시지

하나의 기술이 아니라 문제별 방어선이 겹쳐 전체 흐름을 보호한다.

### 발표 대본

“사전 검증은 확실한 실패를 외부 호출 전에 막습니다. Redis는 같은 멱등키의 동시
실행을 줄입니다. payment_attempt는 Redis 장애 후에도 실행 여부와 최초 응답을
보존합니다. 외부 발행사 orderId 방어는 쇼핑몰 우회 요청을 막습니다. 조건부
UPDATE는 서로 다른 주문이 같은 포인트를 쓰는 경쟁을 막습니다.”

## 14페이지. 외부 발행·Deadlock·재요청 성능 검증 결과

### 핵심 메시지

개선 효과를 HTTP뿐 아니라 외부 호출과 DB 상태로 증명했다.

### 발표 대본

“외부 중복 발행은 2건에서 1건, Deadlock과 잔액 부족 외부 발행은 각각 1건에서
0건으로 줄었습니다. 완료 재요청 100회 평균은 DB-only 8.118ms에서 Redis cache
2.588ms로 줄었습니다.

이 수치는 로컬 순차 재요청의 방향성 비교이며 운영 TPS로 과장하지 않습니다. 모든
실험은 HTTP 응답, provider_voucher, voucher_purchase, payment_attempt와 잔액
결과를 evidence로 저장했습니다.”

## 15페이지. 분산 멱등성·원자적 차감·보상 처리 결론

### 핵심 메시지

문제를 더 앞에서 막고, 결과는 영구 보존하고, 공유 자원은 DB에서 원자적으로 변경했다.

### 발표 대본

“이 프로젝트를 통해 멱등성은 중복 요청을 단순히 무시하는 것이 아니라 요청의
동일성을 검증하고 최초 응답을 다시 반환하는 것임을 확인했습니다. 또한 Redis,
DB 중복 방지, 조건부 UPDATE와 보상 취소가 서로 다른 문제를 담당한다는 점을
구현과 실험으로 구분했습니다.

다음 과제는 외부 쿠폰 발행 전 포인트 예약, 취소 실패를 영속화하는 Outbox,
Redis 운영 구성과 Testcontainers 동시성 회귀 테스트입니다.”

## 전체 1분 요약

“동일 주문을 동시에 호출했을 때 외부 쿠폰이 두 장 발급되고 내부에서는 Deadlock이
발생하는 Legacy 흐름을 재현했습니다. 먼저 payment_attempt에 PROCESSING 상태를
saveAndFlush로 즉시 저장해 외부 호출 전에 orderId 처리권을 선점했습니다. 외부
발행사에도 orderId 중복 방지를 추가하고, 잔액 부족은 외부 호출 전에 차단했습니다.

두 인스턴스 환경에서는 Redis 분산락과 결과 cache를 추가하되 MySQL에 최초 응답을
저장해 Redis 장애에도 같은 결과를 반환했습니다. 서로 다른 주문의 잔액 경쟁은
조건부 UPDATE로 해결했습니다. 그 결과 외부 중복 발행은 2건에서 1건, Deadlock과
중복 차감은 0건이 되었고, 결과를 HTTP와 DB evidence로 검증했습니다.”
